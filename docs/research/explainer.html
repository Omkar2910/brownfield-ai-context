AI context for brownfield services

Keep agent context small, owned, and tested like code

How to create, use and keep updating the context that coding agents read, for a UI service and a backend service, with OpenSpec for behaviour and hooks, skills and one custom agent for upkeep.

The idea in one minute

Context goes stale for one reason: updating it depends on someone remembering. The fix is a system where each job goes to the cheapest thing that can do it reliably. Scripts detect drift, skills carry out the fix, one steward agent owns the upkeep, CI enforces it, and humans approve.

Hooks + CIDetect

Deterministic checks on every edit, session end, commit and PR.

SkillsDo

Repeatable procedures: bootstrap, refresh, story to change.

Steward agentOwn

One role with limited tools that maintains context files only.

PeopleApprove

Every context change merges through a reviewed PR.

Golden tasksMeasure

Past stories re-run to prove context helps, or revert it.

Short answers to your questions. Hooks: yes, but as detectors that remind and block once, not as writers. Custom agent: yes, one narrow steward that proposes PRs, never auto-merges. Quarter/sprint/story: use them as review cadences, not as document folders. How much context: as little as passes your golden tasks; start with an always-on budget of about 1,500 tokens.

What "context" actually is

"Internal context" is really seven layers with different owners and lifetimes. Most confusion between a trainer's skill and an ad-hoc prompt comes from mixing them into one pile of files.

loaded on every requestloaded when matching files are touchedloaded on demand or queried
L0Platform rules Keycloak = login only, CIAM = permissions, error envelopesystem-context
L1Repo core commands, non-obvious rules, pointers. Under 100 lines.AGENTS.md
L2Scoped rules Angular components, Spring controllers, Flyway migrations.instructions.md
L3Service knowledge architecture, known traps, why odd code existsdocs/context/
L4Behaviour what the system does today, as requirements + scenariosopenspec/specs/
L5Task one story's proposal, design, tasks, delta specsopenspec/changes/
L6Retrieval call graph, contracts. Queried, never pasted.Graphify, OpenAPI

Each service repo owns L1–L3. A shared system-context repo owns L0, contracts, skills, the steward agent and, for a tightly coupled UI + backend pair, all OpenSpec specs. For a story that crosses services, open one multi-root VS Code workspace with all three repos.

Hooks: where to add them, and what they should do

Verdict: use hooks to detect and remind, deterministically and in milliseconds. Do not use hooks to write context with an LLM on every edit. That is slow, costs tokens on every tool call, and produces exactly the unreviewed generated context that research found makes agents worse.
WhereEventWhat it doesWhy there
Agent: session startSessionStart / sessionStartAdds a short health line: context file count, broken anchors, active OpenSpec changesCheap orientation; replaces "read everything first" prompts
Agent: after an editPostToolUse / postToolUseIf the edited file is anchored by a context line, names that lineThe agent has the change in mind right now, so the fix is cheapest here
Agent: before finishingStop / agentStopChecks broken and stale anchors once; blocks a single time with the listOne consolidated check per session, with no loops
Steward runs onlyPreToolUse / preToolUseDenies any edit outside context filesTurns "edits context only" from a request into a hard rule
Gitpre-commitRefuses commits with broken anchorsCovers humans and any tool without agent hooks
CIPR pipelineSame check against the target branch; warn first, then blockingThe only place you can enforce across everyone
OpenSpecoperations.archive.guidanceMakes archive list the context lines a change affectsEvery story ends with an archive, so it is a free, reliable trigger
ScheduleWeekly pipelineRuns the check; on findings, the steward opens a fix PRSafety net for what slipped through

Why hooks help

  • Deterministic: nobody has to remember
  • Feedback lands while the agent still has the change in mind
  • No tokens unless there is a finding
  • One script serves Claude Code and Copilot

Limits to plan around

  • Agent hooks run only inside agent sessions, so git and CI are still needed
  • Copilot hooks in VS Code are a preview feature; formats may change
  • Slow or noisy hooks get disabled; keep them under a second
  • A Stop hook that blocks every time traps the agent; block once

In the kit: system-context/hooks/context-hooks.cjs (Node, no dependencies), wired in .claude/settings.json and .github/hooks/context.json in each service repo, plus system-context/githooks/pre-commit.

Should you build a custom agent for context?

Yes, one narrow steward

A context steward is worth it because upkeep is a role, not a single procedure. It has one job (maintain context files), limited tools, fixed modes, and a hard rule that it never touches application code. It does not replace skills; it runs them.

PieceIs aOwns
Hooks + CIDetectorFinding drift, every time, for free
SkillsProcedurecontext-bootstrap, context-refresh, story-to-change, onboard-me
context-steward agentRoleModes: bootstrap, refresh, audit, prune, sprint-digest, quarterly-review
Tech leadApproverMerging every context PR

Pros

  • One consistent way to maintain context across teams
  • Restricted tools and a guard hook make it safe to run headless
  • Same agent file for Copilot (.github/agents) and Claude Code (.claude/agents)
  • Can run on a schedule and open PRs

Cons and guardrails

  • LLM-written context can be wrong: anchor every fact and review every PR
  • Agents tend to add; give it budgets and a prune mode
  • It is one more file to maintain; keep it in the shared repo
  • Never let it auto-merge

Do not build one mega-agent that writes specs, code and context. Spec work stays in OpenSpec (/opsx:*), code in the normal agent, context in the steward. Separate roles keep each one's instructions short.

Quarter, sprint, story: cadence, not folders

Good instinct, different shape

Organising context documents by quarter and sprint creates many dated files. An agent cannot tell which is current, every one costs tokens, and nobody maintains old ones. Keep facts where they live by lifetime, and use the calendar to decide when you review.

CadenceWhat happensEffortAgents load it?
Every edit / session / commitHooks detect drift automaticallyNoneOnly the reminder
Every storyOpenSpec change folder (dated on archive), specs merged, affected context lines refreshedPart of the storySpecs, on demand
Every sprintSteward writes a 5-bullet digest to CHANGELOG.md; review #agent-miss tags15 min in retroNo, human-facing
Every quarterSteward's review table; re-run golden tasks; prune; tidy specs per domainAbout 1 hour per teamResults only

Story history already exists for free: archived OpenSpec changes live in openspec/changes/archive/YYYY-MM-DD-<id>/. That is your story-level record, without anyone writing extra documents.

How much context is enough?

A 2026 ETH Zurich study tested coding agents with no context file, an LLM-generated one and a developer-written one. Generated files lowered success in most settings and added 20–23% cost. Human-written files helped about 4% on average. Agents follow what you write, so every unnecessary rule is work they will do.

L0 ~400
L1 AGENTS.md ~1,100
0always-on budget ≈ 1,500 tokens
Context typeStarting budgetTest
Always-on (L0 + L1)~1,500 tokens; AGENTS.md under 100 linesEach line would cause a real mistake if missing
Scoped instruction fileUnder ~50 lines each, tight applyToFires only on files it governs (check References)
Story context packUnder ~150 linesOnly domains this story touches
Everything elseNo limit, never auto-loadedReachable by link, skill or query

Signs of too much

  • Agents take more steps and read more files for the same task
  • Rules conflict or repeat each other
  • Lines describe things a grep finds in a minute
  • Cost per story rises with no quality gain

Signs of too little

  • The same #agent-miss comment appears twice
  • Agents ask the same question every session
  • New joiners ask humans about the same trap
  • Agents use Keycloak roles instead of CIAM, or similar platform slips

The budgets are starting points. The real answer comes from golden tasks: keep 3–5 past stories with known-good diffs, run a fresh agent with each context variant, and keep the variant with the higher pass rate and fewer steps.

Run the demo kit

Pick a track. Track A needs no AI tool and shows the core idea in five minutes. Track B is the full story in VS Code with Copilot. Track C is the same with Claude Code. On Windows, run the shell commands in Git Bash.

  1. Get the repo and set up the three demo repos

    Needs Git and Node 18+. The setup script copies the three folders to ~/context-demo and makes each a git repo.

    git clone https://github.com/Omkar2910/brownfield-ai-context.git
cd brownfield-ai-context/demo-kit
bash setup-demo.sh            # creates ~/context-demo/{report-service,report-ui,system-context}
cd ~/context-demo

  2. Run the context check on clean repos

    bash system-context/scripts/check-context.sh report-service report-ui system-context

    Expect: 0 error(s), 0 warning(s).

  3. Simulate a refactor and watch it get caught

    cd report-service
git mv src/main/java/com/example/report/api/ReportController.java \
       src/main/java/com/example/report/api/ReportRowsController.java
echo "// tweak" >> src/main/java/com/example/report/query/ReportQueryService.java
bash ../system-context/scripts/check-context.sh .

    Expect: ERROR AGENTS.md: anchor not found for the renamed controller.

  4. See what the agent hooks would say

    Feed the hooks the same JSON an agent would send.

    H=../system-context/hooks/context-hooks.cjs
echo '{"hook_event_name":"SessionStart"}' | node $H session-start
echo '{"hook_event_name":"PostToolUse","tool_name":"Edit","tool_input":{"file_path":"src/main/java/com/example/report/query/ReportQueryService.java"}}' | node $H post-edit
echo '{"hook_event_name":"Stop","session_id":"demo"}' | node $H stop

    Expect: a health line naming the broken anchor; a note that AGENTS.md:18 references the edited file; a "decision":"block" listing what to fix. Run the stop line again: it stays silent, so the agent cannot loop.

  5. Turn on the git hook and try to commit

    git config core.hooksPath ../system-context/githooks
git commit -am "rename controller"

    Expect: commit refused until the anchor in AGENTS.md is fixed. Undo with git reset --hard.

  1. Prerequisites

    Track A setup done; VS Code with GitHub Copilot Chat; Node 20+; OpenSpec CLI.

    npm install -g @fission-ai/openspec@latest
cd ~/context-demo/system-context && openspec store register "$(pwd)"   # beta; see fallback in DEMO-SCRIPT.md
cd ../report-service && openspec init     # choose GitHub Copilot; keep the existing config.yaml
cd ../report-ui && openspec init

  2. Open the multi-root workspace

    code ~/context-demo/system-context/workspaces/report-platform.code-workspace

    Ask in Agent mode: "What rules apply if I add a button to the report grid? List the files you used." Expand References: Angular rules and the CIAM platform rule load, Spring rules do not.

  3. Enable hooks (preview)

    Hooks are in .github/hooks/context.json in each service repo. If your VS Code version gates them, turn on hooks in settings (check Chat: Open Customizations → Hooks). The session-start health line should appear in the agent's context.

  4. Explore and propose REPORT-142

    /opsx:explore REPORT-142: export the filtered ratings report to Excel. Read the consumer brief and both repos' AGENTS.md first.
/opsx:propose add-report-excel-export

    If generation is slow, open the prepared change in system-context/openspec/changes/add-report-excel-export/.

  5. Apply the producer slice and watch the hooks

    /opsx:apply add-report-excel-export — do section 1 (report-service) only

    When the agent edits ReportQueryService.java, the post-edit hook names the AGENTS.md line. When it finishes, the stop hook runs once.

  6. Run the steward

    Pick context-steward from the agent dropdown and type "audit report-service". Then "sprint-digest".

  7. Archive and onboard

    /opsx:archive add-report-excel-export
/onboard-me

  1. Start Claude Code with all three repos

    cd ~/context-demo/report-service
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../report-ui --add-dir ../system-context

    Hooks load from report-service/.claude/settings.json. Skills in system-context/.claude/skills load automatically from the added directory (create it with ln -s ../.github/skills system-context/.claude/skills).

  2. Check the hooks are active

    Type /hooks to list them. Ask "what is the context health?" and the agent will quote the session-start line.

  3. Run the story

    Same OpenSpec commands as Track B. Then ask Claude to use the context-steward subagent: "use context-steward to audit report-service".

  4. Headless steward with the guard

    This is how the weekly pipeline runs it. The guard hook refuses edits outside context files.

    claude -p "Mode: audit ." --agent context-steward \
  --add-dir ../system-context \
  --settings ../system-context/agents/steward-settings.json

Explaining it upward

Lead with the problem and the measure. The tooling is the least interesting part for management.

Problem

In existing services, agents guess conventions and contracts. Context files go stale within a sprint, and every developer prompts differently, so results vary and review effort rises.

Approach

Treat context as code: small files owned per service, shared contracts and platform rules in one repo, OpenSpec for behaviour, automatic drift checks, one steward agent, human approval.

Why it is safe

Nothing merges without review. The agent edits context only. Every check also runs in git and CI, so it does not depend on preview features.

Effort (estimate)

About a day per repo to bootstrap and prune, 15 minutes per sprint, 1 hour per quarter. CI cost is seconds per PR.

What we measure

Golden-task pass rate vs no context; agent steps and tokens per story; #agent-miss trend; new-joiner time to first merged story.

The ask

A 4-sprint pilot on one UI + backend pair, about an hour a week of tech-lead time, approval for the PR check, and optionally API access for the weekly steward.
