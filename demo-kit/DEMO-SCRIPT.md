# Demo script — REPORT-142 across UI + backend (about 20 minutes)

**Story REPORT-142.** As a credit analyst, I want to export the filtered ratings report to Excel
so I can share it offline.
- Export button only for users with CIAM permission `REPORT_EXPORT`
- Uses the grid's applied filters and sort
- Over 50,000 rows → HTTP 422 `REPORT_TOO_LARGE`, shown as a toast
- File name `ratings-report-<yyyyMMdd>.xlsx`

The message of the demo: **context is layered, owned per repo, joined per story, and tested like code.**

---

## 0. Before the session (10 min, once)

```bash
npm install -g @fission-ai/openspec@latest
# put report-service, report-ui and system-context side by side, each a git repo
cd system-context && git init -q && git add -A && git commit -qm "context store"
openspec store register "$(pwd)"            # stores are beta: check `openspec store --help`
cd ../report-service && openspec init        # choose GitHub Copilot and/or Claude Code; keep config.yaml
cd ../report-ui && openspec init
```
If `store register` complains that the folder is not a store, run `openspec store setup`
(name `system-context`), then copy this kit's `system-context/` content into the folder it creates.
No time for stores? Use the fallback at the end of this file.

Optional: `graphify .` in each service repo and `graphify copilot install` (or `claude install`).

## 1. Open the workspace (2 min)

Open `system-context/workspaces/report-platform.code-workspace`.

Ask Copilot (Agent mode):
> What rules apply if I add a button to the report grid? List the files you used.

Expand **References**: show `report-ui/AGENTS.md`, `angular-components.instructions.md`, and the
CIAM platform rule. Point out that Spring rules did **not** load — scoping works.

Claude Code variant:
```bash
cd report-service
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../report-ui --add-dir ../system-context
```

## 2. Show the layers (3 min)

Walk the folders in this order and say one sentence each:
1. `system-context/context/platform/` — L0, written once for every repo.
2. `report-service/AGENTS.md` — L1, under 60 lines, only non-obvious rules, each with an anchor.
3. `.github/instructions/*.instructions.md` — L2, loads only for matching files.
4. `docs/context/known-traps.md` — L3, loaded on demand; every line came from an incident.
5. `system-context/openspec/specs/` — L4, behaviour as requirements + scenarios.
6. `system-context/contracts/report-service/consumer-brief.md` — generated by the producer.

## 5. Propose and review (4 min)

> /opsx:propose add-report-excel-export

If live generation is slow, open the prepared folder:
`system-context/openspec/changes/add-report-excel-export/`
- `proposal.md` — affected repos, contract change, new permission
- `design.md` — decisions + request/response examples
- `tasks.md` — task 0 platform ticket, producer first, then consumer
- `specs/report-export/spec.md` (ADDED) and `specs/report-grid/spec.md` (ADDED)

This is the **tech-lead review gate**: no code until this is approved.

## 6. Apply (2 min, show the start)

> /opsx:apply add-report-excel-export — do section 1 (report-service) only

Show the agent adding `@RequiresPermission("REPORT_EXPORT")` and integration tests without
being told — that came from L1/L2 + config.yaml rules.

## 7. Catch drift (2 min)

Rename the controller to simulate a refactor, then run the check:
```bash
git -C report-service mv src/main/java/com/example/report/api/ReportController.java \
                         src/main/java/com/example/report/api/ReportRowsController.java
bash system-context/scripts/check-context.sh report-service report-ui
```
Expected: `ERROR AGENTS.md: anchor not found -> .../ReportController.java`.
With `--base main` it also warns when anchored code changed but the context file did not.
Undo with the reverse `git mv`.

## 7b. Show the hooks catching it inside the agent session (2 min)

Leave the rename in place and ask the agent to finish any small task. When it tries to stop,
the `stop` hook blocks once and lists the broken anchors; the agent fixes the context line.
Then edit `ReportQueryService.java` through the agent: the `post-edit` hook tells it which
`AGENTS.md` line references that file. No human had to remember.

Without an agent, show the same with the git hook:
```bash
git -C report-service config core.hooksPath ../system-context/githooks
git -C report-service commit -am "rename"     # refused: anchor not found
```

## 8. Archive (1 min)

> /opsx:archive add-report-excel-export

Show `openspec/specs/report-export/spec.md` now exists and the change moved to
`changes/archive/<date>-add-report-excel-export/`. Archive guidance asks the agent to list
context files to update — run `/context-refresh` to do it.

## 9. Onboard a new joiner (1 min)

> /onboard-me

## Close (30 s)

Three takeaways:
1. Context per repo, joined per story — never one merged blob.
2. Always-on context stays tiny; everything else loads on demand or is queried.
3. Context is code: owned, reviewed in the same PR, checked in CI, and measured with golden tasks.

## Fallback without OpenSpec stores (beta)

1. In each service repo delete the `store:` line from `openspec/config.yaml` and run `openspec init`.
2. Copy `system-context/openspec/specs/report-query` into `report-service/openspec/specs/` and
   `report-grid` into `report-ui/openspec/specs/`.
3. Create the change in each repo with the same id `add-report-excel-export`:
   backend gets `specs/report-export` + tasks section 1; UI gets `specs/report-grid` + section 2.
4. Keep `system-context` for platform rules, contracts, skills and the workspace file.
